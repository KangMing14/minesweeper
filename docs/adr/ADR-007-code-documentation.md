# ADR-007: Code documentation

- Status: Accepted
- Date: 2026-11-09
- Task: M0-T06
- Settles: none

## Context

Many conversations, some of them with an AI assistant that starts with no memory of the code, will read and extend this repository. Names and doc comments are what carry intent from one conversation to the next. Documentation that is only asked for by convention decays, so the rules have to fail a build. The spec (section 7.2) asked for Doxygen-style doc comments, and Doxygen does not support TypeScript first-class.

## Decision

Doc comments use TSDoc, are enforced by lint, and the API reference is generated by TypeDoc.

- **What must be documented.** Every exported class, interface, type, function, enum and constant has a TSDoc comment: a one-sentence summary, then `@param`, `@returns` and `@throws` where they apply. `@example` is required on the public API of `engine` and `protocol`. `@remarks` records invariants and contracts, `@internal` marks members exported only for tests, and `@deprecated` names the replacement. Non-exported code is documented when its purpose is not obvious from its name.
- **Inline comments say why, not what.** They are required for non-obvious algorithms, invariants, performance trade-offs and workarounds. Commented-out code is not allowed. Every TODO names a task, `// TODO(M6-T04): ...`, and `scripts/check-todos.mjs` fails on any other.
- **Lint.** `eslint-plugin-tsdoc` validates comment syntax everywhere. `eslint-plugin-jsdoc` requires doc comments on exports and `@example` on them: an error in `engine` and `protocol`, test files exempt. In `apps/*` the doc-comment requirement is a warning until M5-T03, which flips it to an error. Fixtures in `tools/lint-fixtures/` prove each rule fires.
- **API reference.** TypeDoc builds the reference for `engine` and `protocol` in `packages` mode, and TypeDoc warnings are errors in CI. The output goes to `docs/api/`, is ignored by Git and is published as a CI artifact, never committed.
- **Definition of done.** Every task's acceptance criteria include that exported symbols are documented and that lint and TypeDoc pass.
- **Not used.** Doxygen. It targets C-family languages and has no first-class TypeScript support; TSDoc with TypeDoc gives the same result, structured doc comments rendered as an HTML reference.

## Consequences

- A missing doc comment, a malformed TSDoc tag or a bare TODO fails CI, so the documentation cannot silently fall behind the code.
- The machine-enforced rules cover presence and syntax, not quality. The completeness of `@param` and `@returns` is not machine-enforced, and TypeDoc's `notDocumented` validation is deliberately off, because the spec requires comments on exported symbols, not on every member. Review is where quality is checked.
- `jsdoc/require-example` sees only declarations exported in the same statement as their definition (`export function f`), so a symbol exported through a separate `export { f }` or re-export is not checked for an example. Authors must keep that in mind.
- `eslint-plugin-tsdoc` 0.5.4 pulls in its own older `@typescript-eslint/utils`, which causes one accepted peer-dependency warning on `pnpm install`; revisit when the plugin releases a newer version.
- Writing the examples takes time on every public symbol of `engine` and `protocol`. That is accepted because those two packages are the long-lived contract.
- The warning-to-error flip for `apps/*` at M5-T03 is a known future task that will surface any undocumented exports written before it.

## Alternatives

- **Doxygen.** Rejected for the reason above.
- **No enforcement, documentation by convention.** Rejected: unenforced documentation decays across many conversations.
- **TypeDoc `notDocumented` validation for every member.** Rejected: it would force comments on trivial members, against the spec's scope.
- **Requiring doc comments on all code, exported or not.** Rejected as noise; the rule is that non-obvious code is explained.
- **Committing the generated reference.** Rejected: generated artifacts are not committed (ADR-006).
